JOURNAL WRITING — PROJECT EXPLAINER (3 clients)


A complete description of what this project is, how it is built, and the reasoning behind every major decision. This single codebase serves three clients — Dhanashri, Pratiksha and Siddhesh — from one repository, sharing one engine while keeping their stories, themes and identities completely separate.


1. WHAT IT IS, IN ONE SENTENCE

Journal Writing is an aesthetic, scrapbook-style journaling system where each client privately writes illustrated journal "stories" and everyone else can read them, hosted entirely on free static hosting (GitHub Pages) with no server and no database.

It hosts three independent journals from one repo: Dhanashri's Journal (pastel lavender theme), Pratiksha's Journal (pastel blue theme), and Siddhesh's Journal (rose pink theme). Each has a public side (a homepage of story cards plus a reader with PDF export) and a private editor (admin.html) for creating, publishing, editing and deleting stories.


2. WHY MERGE THE CLIENTS

All three journals are the same product with a different coat of paint. As separate projects, every change had to be made more than once, and the copies slowly drifted out of sync (different washi sets, different layer controls, and so on).

Merging fixes that. The entire engine — fonts, backgrounds, the photo/text/caption styling, the page renderer, the publishing logic — lives in one shared assets/ folder. A change made there reaches all three clients at once, so they can never drift again. Only each client's identity (which folder its data lives in, its title, its theme) is separate.


3. FILE STRUCTURE

Journal-Writing/ is one GitHub repo served by GitHub Pages.

assets/ is the shared brain (edit once, all three clients update): core.js holds the client-agnostic engine (fonts, backgrounds, renderer, styling, GitHub helpers); style.css holds the structure plus all three colour themes (switched per client); backgrounds/ holds bg01.jpg to bg28.jpg (shared decorative page art); PROJECT.txt is this document; Setup.txt is the step-by-step setup and hosting guide.

Dhanashri-Journal/ is client A (pastel lavender): index.html, story.html, admin.html, and data/ (index.json plus posts/<id>.json). Pratiksha-Journal/ is client B (pastel blue) with the same three pages and its own data/. Siddhesh-Journal/ is client C (rose pink) with the same three pages and its own data/.

Folder names have no spaces, so the live URLs contain no %20: https://laxman-sidhu.github.io/Journal-Writing/Dhanashri-Journal/ , .../Pratiksha-Journal/ , and .../Siddhesh-Journal/ .


4. HOW A CLIENT KNOWS WHO IT IS (THE ONLY CLIENT-SPECIFIC CODE)

The shared core.js contains no client identity. Each client's three HTML pages declare who they are in a tiny block placed immediately before core.js loads — for example, window.JOURNAL_CLIENT = { USERNAME: "laxman-sidhu", REPO: "Journal-Writing", DATA_DIR: "Pratiksha-Journal/data", TITLE: "Pratiksha's Journal" } — followed by the shared script tag for ../assets/core.js.

The data-client attribute on each page (for example data-client="pratiksha") selects that client's colour palette from the shared stylesheet. That, plus the block above, is the entire difference between the clients.


5. THE DATA-ISOLATION GUARANTEE (WHY ONE EDITOR CANNOT WRITE ANOTHER'S FOLDER)

This was the central worry when merging, so it is handled explicitly. A GitHub write has two independent parts: the token (an HTTP header) only answers "may you write to this repo at all?" and carries no folder information, while the path (in the URL) is the only thing that decides which file is written.

Every read and write in admin.html is built from this client's own DATA_DIR through a small helper, ghPath, which joins DATA_DIR with the relative path and URL-encodes it. All calls go through it, so a publish always lands in this client's own posts folder.

Because DATA_DIR is hard-coded into each client's own pages, an editor can only ever build paths under its own data folder. It is deterministic: the same token pasted into any editor changes nothing about the destination — the folder is fixed by the page, not by the key.

The honest caveat: a fine-grained token grants write to the whole repo, not a single folder, so the separation above is enforced by the code, not by GitHub. If the same trusted person publishes all journals (the intended setup), there is no risk. If the clients were mutually untrusted, true isolation would require separate repos. See the Tokens section of Setup.txt.


6. THE CORE IDEA: REPO-AS-DATABASE

GitHub Pages is static hosting — it serves files and runs no code. So the Git repository is the database. Every story is a small JSON file committed into the repo. Public pages just fetch those static files and draw them, which makes "read-only for visitors" automatic, because there is no write path in the public pages at all.

Publishing works without a server because the editor talks directly to the GitHub Contents API from the browser, authenticated with a token. One API call commits a file; GitHub Pages rebuilds and the new content appears within about a minute, with no backend, no build step and no hosting bill.

When the editor presses Publish, it writes <DATA_DIR>/posts/<id>.json (the story, with photos embedded), then reads, updates and writes back <DATA_DIR>/index.json (the homepage list). Editing includes the file's current sha; deleting sends a delete and prunes the index.


7. THE EDITOR'S FEATURES

The editor is laid out as a fixed ribbon pinned to the top of the window, in the spirit of Word. The first row carries the story's identity and the document actions (Background, New, Import, Save draft, Open, key, Publish). The second row is always-on commands grouped as Insert (Text, Photo, Doodles), Edit (Undo, Redo, Duplicate, Delete), Arrange (send behind, bring to front, centre on the page) and Pages (the page tabs). The third row is contextual: it swaps its contents for whatever is selected — text, photo, caption, border or doodle controls. That third row has a fixed minimum height, so showing or hiding a bar never shifts the canvas underneath it, which is what made the previous floating palettes feel jumpy. The old floating bottom toolbar is gone; everything lives in the ribbon.

A freeform scrapbook canvas where elements are placed anywhere.

Selecting and moving: every item is grabbed anywhere on its body, not by a handle in one corner. A text box is always in exactly one of two modes, and it is never ambiguous which:

  - MOVE mode (the default). One click on an unselected box selects it; dragging from anywhere on it moves it.
  - TYPE mode. A double-click drops the caret in and starts typing. The box is then held still: dragging is off, so a stray gesture cannot nudge it while you write.

Leaving TYPE mode: click the empty part of the box (not the words) and it returns to MOVE mode and begins the move in that same gesture, so one click-and-drag both stops typing and repositions the box. Clicking the words instead just moves the caret, which keeps ordinary text editing intact. Escape also leaves typing and keeps the box selected; Escape again deselects. Whether a click landed on the words is decided by hit-testing the real glyph rectangles rather than guessing from padding, so it stays right at any font, size or alignment. Photo captions work the same way.

On touch, where a double-tap is hard to land, tapping an already-selected text box starts typing.

The subtle part is that MOVE mode must not swallow the double-click. Capturing the pointer on pointerdown retargets the later click and dblclick events to the captured element, and calling preventDefault there suppresses the compatibility mouse events outright; either one silently kills the double-click that starts typing. So the drag arms on pointerdown but only captures the pointer once the pointer has actually travelled about three pixels. A click therefore stays a click, and the side benefit is that a shaky click can no longer nudge an item by a pixel.

Resizing: every item has eight handles — the four corners and all four walls. West and north handles hold the opposite edge still, so a box grows away from where you pull. Text boxes resize width from the east/west walls and height from the north/south walls; that height is stored as a MINIMUM, so longer text still grows past it and can never be clipped, and a Fit button in the ribbon drops the manual height to shrink the box back around its text. Photos, image stickers, doodles and tape keep their proportions: width drives height, so any handle scales them evenly.

Placing things precisely: dragging snaps to the page centre line and to every other item's left, middle, right, top, centre and bottom, drawing a guide line where it caught. Hold Alt while dragging to ignore the guides. Arrow keys nudge the selection by one pixel (Shift for ten), Ctrl+D duplicates it, Delete removes it.

Overflowing the page: the editor no longer clips items at the page edge, so a text box slid halfway off the left is fully visible while you work on it, exactly as in Word. The reader still clips at the page edge, again as in Word, where a box pushed off the paper shows on screen but not in print. Items may be parked up to 240px outside the page.

Text boxes: a curated set of around forty fonts where every entry renders visually unique — mostly free Google web fonts (identical on every device) plus widely-installed classics such as Times New Roman, Cambria, Courier New, Daun Penh and Bodoni MT. Decorative named fonts that were not installed on most devices used to appear as identical duplicates of their shared fallback, so they were removed; a FONT_ALIASES map in core.js keeps any story already published with one of those keys rendering exactly as before, size, bold/italic/underline, four alignments with proper horizontal-bar icons (like Word / Google Docs), an adjustable paragraph/line spacing control (1.0–3.0), a text colour and a separate text-box fill, and free rotation. The font dropdown previews each font name in its own typeface. The editor's font dropdowns group similar styles together under labelled headings — Handwritten & Casual, Elegant Script & Calligraphy, Brush & Retro Script, Serif & Classic, Clean & Modern, Monospace — so related fonts sit one after the other (the grouping order lives in core.js as FONT_GROUPS; any font missing from it is auto-appended to a trailing More group). Bold, italic and underline work on a selection inside a box — pick a word or two and only those change, with no separate box needed — as do strikethrough, bulleted and numbered lists, and clear-formatting. FONT, SIZE and COLOUR now follow the same rule: highlight a word or a line, change the font, and only that run changes; with nothing highlighted the control styles the whole box exactly as before.

Two details make that work. First, clicking a ribbon control can blur the box and drop the highlight, which would silently turn "change these words" into "change everything", so the last real selection made inside a text body is remembered and restored just before a command runs. Second, a repeat tweak — nudging a size, or dragging through a colour picker — would otherwise wrap a fresh span around the previous one on every single change and nest without bound, so when the selection already lines up exactly with an existing span that span is restyled in place instead.

Photos: move, resize, rotate, crop and caption, with looks Plain, Border and Frame (the old separate Card option was merged into Frame: a white frame is the classic photo-card look). Border now has adjustable colour and width, with the original thin white border as the default. New: every photo look also has an adjustable corner rounding control — from 0 (completely square) up to fully rounded — working exactly like the border-width stepper; unset keeps the original subtle rounding. Fixed and new: Plain keeps PNG transparency, so a cut-out image such as a no-background aeroplane shows only the subject, with no box and no black fill — uploads with transparency are now saved as PNG instead of JPEG (which has no alpha channel). Shadow is now an independent toggle that can sit on any look — framed, card, border or a plain cutout — and turns fully off when unchecked. New: the caption has its own font, size and colour controls.

Videos: added by DIRECT link rather than by upload, because a clip cannot live inside the story file. A phone video is tens of megabytes and base64 inflates it by a further third, which would blow past the autosave limit (localStorage caps a draft near 5MB), make every publish a huge commit, and force every reader to download the whole clip before the page could draw. So a video element stores only the LINK plus a thumbnail image you choose yourself, and the thumbnail is the sole thing embedded, exactly like a photo.

The editor asks for two things: the link and the thumbnail. The link must point at a real file — an .mp4 or .webm served over https, which is what a Cloudinary upload gives you — and it plays in the browser's own <video> element with native controls. YouTube and Vimeo links are refused with an explanation rather than accepted, and that refusal is deliberate: their embeds are iframes that carry their own branding, channel name, title, and like and share buttons onto the page, none of which can be switched off (modestbranding is deprecated and does nothing, and hiding the chrome with CSS breaks their terms). A Shorts embed is the worst of these. An iframe also cannot be rasterised into the PDF, and it swallows pointer events. A direct file has none of those problems. The thumbnail is required, and the editor refuses to save without one, because it is the only thing a closed page and a printed page can show.

Videos take the same looks as photos: Plain is the clip on its own, Card puts it on a white photo-card with the caption underneath, and the card colour, corner rounding, shadow and caption styling all work the same way, so a clip and a photo sitting side by side on a page match.

Every surface draws the same FACADE: the thumbnail with a play badge over it. The editor shows only that, never a live player, because an iframe swallows pointer events and would fight the drag, resize and rotate handles. The reader shows it too and swaps in the real player when the tile is clicked, so nothing loads until someone asks for it, several clips can share a page without all of them loading, and starting one clip returns the others to their thumbnails instead of playing over each other.

The badge is a border-radius circle with a CSS-border triangle inside it, not an inline SVG. That is a deliberate constraint of the PDF path, described in section 8.

Stickers: an emoji library, paste-any-emoji, and upload-your-own image with PNG transparency kept. Washi tape: a grid of pastel tapes, striped or plain. Doodles: stars, arrows, lines, hearts and more, each recolourable with adjustable weight. Layering: send an item behind or bring it in front of others. Plus multiple pages per story, per-page backgrounds (grid, dots or plain plus 28 decorative images), a cover photo picker, autosave, Save draft and Import JSON, and Publish, Open and Delete.


8. THE DATA MODEL

data/index.json is a list of lightweight entries (id, title, date, small thumbnail). data/posts/<id>.json is one complete story, shaped as id, title, date, and pages, where each page has a paper and a list of elements.

Every element has a position in a fixed 760-pixel design space plus type-specific fields. A text element has content, an optional html field for rich inline runs, font, size, bold, italic, underline, align, spacing (line/paragraph spacing multiplier), color, fill, width, an optional h (a manual MINIMUM box height in px; unset means the box sizes itself to its text) and rotation. A photo has src, caption, style (card, plain, frame or border), frameColor, borderColor, borderWidth, radius (corner rounding in px; 0 = square, unset = the classic default), an independent shadow flag, capFont, capColor, capSize, noCap, width and rotation. A video has src (the direct file link), kind (always file), poster (the chosen thumbnail as a data URL), caption plus the same caption styling fields as a photo, style (plain or card), frameColor, radius, an independent shadow flag, width and rotation. A sticker has emoji, size and rotation. An imgsticker has src, width and rotation. A washi has color, a plain flag, width and rotation. A doodle has key, color, weight and rotation.

Photos and stickers are embedded as data URLs so each story file is self-contained. A video is the deliberate second exception alongside backgrounds: only its thumbnail is embedded, and the clip itself streams from wherever it is hosted, so adding a ten-minute video costs a story file no more than adding a photo.

The PDF export constrains how a video may be drawn. The export rasterises the page with html2canvas, which cannot draw an <iframe> or a playing <video> at all, and which silently drops inline SVG. Two things follow, and both are load-bearing. First, every clip is returned to its thumbnail before the export runs, so the PDF captures an ordinary <img>. Second, the play badge is built from a border-radius circle and a CSS-border triangle rather than an SVG, because html2canvas renders borders and border-radius reliably. Rebuilding that badge as an SVG would make it vanish from the PDF with no error at all, leaving a printed page that looks like a plain photo. Decorative page backgrounds are the deliberate exception — shared files referenced by a short key such as bg04.

Backwards compatible: older stories with no html, h, shadow, spacing, radius or caption-style fields render exactly as before; the new fields are optional and default to the previous look. The rich-text sanitizer now also passes strikethrough and list markup (<s>, <ul>, <ol>, <li>) through to the reader and the PDF export, on the same whitelist-only basis as the original tags.

Homepage identity: all three indexes share the same signature font — Daun Penh (falling back to Cormorant Garamond) for the big heading and the status texts ("opening the journal...", "Could not load stories yet", "No stories yet"), with Playfair Display on the story-card titles. The old kicker strapline above the heading was removed from Dhanashri's and Siddhesh's homepages along with its CSS.

Three further bugs were fixed in the revision after that.

First, the editor could not open or back up a large story. Every read went through the GitHub contents API, which only inlines a file up to 1MB; past that it answers with an empty content field and encoding "none" rather than an error. A story with photos embedded in it is routinely several megabytes, so the editor was decoding an empty string: opening threw and reported "Could not open story", and the JSON backup saved a 0-byte file. ghGet now falls back to the git blobs API, which serves blobs up to 100MB, whenever the contents API returns no inline content. Nothing about the folder routing changed: every read is still built from this client's own DATA_DIR, so each editor still backs up and opens only its own stories.

Second, the PDF export did not reproduce a page faithfully, for two separate reasons. The first was ours: before rasterising, the export set each page holder to width:auto, but a holder's only child is absolutely positioned, so it collapsed to zero width and the page (centred as a flex item) started at the middle of the reader and ran off under the stage's overflow-x:hidden, leaving a band of flat colour down the sides. The second was in html2canvas, and was the one that survived the first fix: it masks a shadow fill against a rectangle the size of the OUTPUT CANVAS but lays that rectangle out in DOCUMENT coordinates, so for a 760x1000 page at scale 2 the mask only reaches document y=2000. Anything past it keeps a winding number of -1 and is filled rather than skipped, so every page below the first had the page's own inset box-shadow colour (--paper-edge) flooded across it, burying the artwork and leaving only a thin frame of it at the edges. Page one, sitting near the top of the document, was only clipped along its bottom edge, which is why the fault looked like a stray band rather than a wholesale repaint. Both are fixed by taking the page out of the reader's layout for the moment it is rasterised: each page is moved into an absolutely positioned host at the document origin, captured there at natural size, and put straight back. That leaves the whole page inside html2canvas's mask rectangle and away from every ancestor clip, so the artwork lands where it should. The page's 1px inset hairline and its rounded corners come off for the capture too: both sit inside the page box, so they printed as a ring of --paper-edge and four tinted corners around otherwise full-bleed art, and a sheet of paper has neither. An explicit width, height and windowWidth are passed as well, so a narrow phone viewport cannot clip the host, and the fill colour now comes from the --pdf-bg token, which had been defined for exactly this and never used. The export runs behind the same loader overlay, which also hides the page while it sits at the document origin.

Third, both slow paths now show a loader instead of appearing frozen. The reader shows a flipping-book animation whose line cycles while a story downloads, and the editor covers importing, opening, downloading, deleting and publishing with the same animation as a full-screen overlay. The overlay call is awaited: these jobs block the main thread, so without giving the browser a frame to paint first the loader would only appear once the work it covers had already finished.

Two bugs were fixed in this revision. First, the decorative page backgrounds now load — their paths are ../assets/backgrounds/..., correct for pages that live one folder deep; previously the relative assets/... resolved inside the client folder and returned a 404. Second, transparent uploads no longer get a black background — the image compressor and the crop now auto-encode to PNG when the image has alpha, and JPEG otherwise.


9. ADDING A FEATURE LATER (THE PAYOFF)

Edit the relevant function in assets/core.js (and, if it has an editor control, the matching handler, which is identical in all three admin.html files). Because the engine is shared, the change applies to all clients at once. The only rule: a bug in the shared core affects every journal, so test before publishing.


10. KNOWN LIMITATIONS

Inline rich text supports bold, italic, underline, strikethrough, lists, line breaks, and per-word font, size and colour. The last three are carried by a <span>, and the sanitizer allows a span to hold ONLY font-family, font-size and color, rebuilding the style attribute from a whitelist rather than passing it through, so nothing else can ride along inside it. A manual text-box height is a minimum only, so dragging the bottom wall upward past the text will not crop it. Classic system and Adobe fonts render as the exact named font only where installed, and fall back elsewhere. Videos are links, so a story depends on the host staying up and the file staying reachable; a deleted clip leaves the thumbnail and a player that will not load. The link is readable by anyone who opens the story JSON, so it is not private. The thumbnail is chosen by hand rather than pulled from the host, which is one more step when adding a clip but is what lets any host work without per-provider thumbnail code. Inline styling covers font, size, colour and the character formats; per-word background fill and alignment remain per-box, because alignment is a block property and a fill would need the same span machinery for very little gain. A fine-grained token grants write to the whole repo, so folder isolation is enforced by the code rather than by GitHub (fine for a single trusted publisher; see section 5). There is a single editor per client and no multi-user conflict handling.
